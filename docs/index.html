Homebridge Camera Utils

Utilities to simplify homebridge camera plugin development

Bounded media ports

Pass a port range as the second RtpSplitter argument to limit its UDP socket. The range includes both endpoints. Existing calls without a range keep automatic port allocation.

const splitter = new RtpSplitter(undefined, {
  portRange: { start: 50100, end: 50119 },
})
try {
  const port = await splitter.portPromise
  // Advertise this port to the media client while the splitter stays open.
} finally {
  splitter.close()
}

The splitter skips occupied ports and rejects portPromise if no port remains. It never falls back outside the range. Close the splitter on session completion or failure to release its socket. Closing during allocation rejects portPromise with AbortError; repeated closure is safe.

This option does not publish Docker ports or select the address advertised to HomeKit. The consuming plugin handles those settings.

GitHub Packages

@motohedgehog/camera-utils is published privately on GitHub Packages and linked to motohedgehog/camera-utils. Consumers can keep importing @homebridge/camera-utils by using an npm alias:

{
  "dependencies": {
    "@homebridge/camera-utils": "npm:@motohedgehog/camera-utils@3.0.1"
  }
}

Use npm:@motohedgehog/camera-utils@latest to follow the latest publication. Both branch builds and stable releases update this default install channel, so it can install development builds.

Configure npm to use GitHub Packages for the @motohedgehog scope. Keep this in your user-level .npmrc or a private project config, and provide a classic GitHub token with read:packages access through NODE_AUTH_TOKEN:

@motohedgehog:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}

Never commit a token or other credentials. In GitHub Actions, GITHUB_TOKEN needs packages: read, and the package's Actions access settings must grant access to each consuming repository.

Publishing

Pushes to latest run the shared Homebridge build and test workflow with coverage, followed by lint. Successful pushes publish <package-version>-dev.<run_id>.<run_attempt>, for example 3.0.0-dev.123.1, using --tag latest. A later branch build replaces a stable release as the default install. Pull requests and manual workflow runs do not publish packages.

To publish a stable version, run npm version patch or npm version X.Y.Z on latest. npm updates package.json and package-lock.json and creates a version commit and vX.Y.Z tag. Push the commit and then its matching tag; the tag version must match both root package versions. A matching pushed vX.Y.Z tag publishes to the npm latest tag after the shared checks. Replace X.Y.Z with the version written to the package files.

Package publications run one at a time across branch and tag builds. Stable releases use npm's default tag, so npm rejects an older stable version after a newer one has been published. Manual CI runs do not cancel push runs.
